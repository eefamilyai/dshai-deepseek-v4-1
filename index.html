Part 2 of 2 · Visual comparison

The same machine, re-plumbed

A standard LLM and DeepSeek V4.1-Flash predict the next token in exactly the same way. Everything in Part 1 still applies. What changes is where the key/value state comes from, how much of it is kept, and how many layers have to run to produce it.

One sentence: a standard transformer gives every layer its own KV cache, computes all layers on every token, and stores that cache at 8–16 bits. V4.1 gives shared KV to most layers, computes only half the layers during prefill, and stores the cache at 4 bits — cutting per-token global KV to 890 bytes and decode FLOPs to nearly flat across context.

01 · The baseline

What a standard transformer actually does

Every layer: own Q, own K, own V, full attention over all earlier tokens.

This is the design from Part 1, and it is what most models still ship. Three properties define it, and all three are the thing V4.1 attacks.

property 1

Per-layer KV

Layer l computes its keys and values from its own hidden state Hl. Sixty layers means sixty distinct KV caches. Nothing is shared.

property 2

Full attention

Each query is scored against every causally visible key. Work grows as O(n²) in context. At 1M tokens, the attention matrix alone is a trillion entries.

property 3

All layers, every token

Prefill and decode both run the full depth. Cost is O(n·L) for the prompt and O(L) per generated token — plus a full cache read every step.

How bad is it at scale? DeepSeek's own V4 paper quantifies it against its predecessor: at a one-million-token context, DeepSeek-V3.2's cost profile is the reference point that V4 was built to beat — and V4.1 was built to beat V4. Those numbers appear in section 8.

02 · The change list

Eight edits, in order of impact

Each one targets a specific line of the cost model — nothing is changed for its own sake.

1 · CED

Causal Encoder–Decoder

Targets prefill compute. Bottom half of the stack is an encoder; the decoder's global KV is projected from the encoder's final hidden state instead of being computed per layer. Prefill runs half the depth.

2 · CSA2

Cross-layer KV & index reuse

Targets cache storage. Layers share one copy of the main KV and indexer keys, and reuse each other's top-K selections. Compresses along sequence, heads, and layers at once.

3 · FP4

4-bit main KV cache

Targets bytes per entry. MXFP4 with a per-16-channel scale, quantized after RoPE. Nearly halves cache size versus V4's FP8. SWA cache stays FP8 for accuracy.

4 · SWA Replay

Bounded replay

Targets persistent storage. Replays only the last window of tokens instead of L×window, so SWA cache never has to be persisted to SSD. Persistent footprint drops to ⅛.

5 · mHC

Single-Pass hyper-connections

Targets the residual stream. Widens it into parallel lanes for a complementary scaling axis, then fuses the update into one kernel that halves activation memory traffic.

6 · Engram

Conditional memory

Targets capability per FLOP. 196B parameters of hash-indexed n-gram memory, addressed cheaply and prefetched from host memory — knowledge that does not need a matrix multiply to retrieve.

7 · DSpark

Speculative decoding

Targets decode latency. Drafts five tokens in one pass with a tiny model, predicts acceptance probability, and verifies as many as the current load justifies.

8 · Vision

Native multimodal

Targets workload shape. A DeepSeek-ViT encoder with 3×3 pixel-unshuffle cuts visual tokens 9×, and images flow through the same backbone as text.

Read the targets down the list: prefill compute, cache storage, bytes per entry, persistent storage, residual width, knowledge density, decode latency, modality. Eight distinct bottlenecks, eight separate fixes. This is why the model is not "a tweak" — it is a re-derivation of the stack around a cost model.

What the left stack stores

N layers × their own K and V. At long context this is the single largest memory consumer, and every one of those bytes must be read from HBM on every decode step.

What the right stack stores

A small number of KV "generators" near the bottom. Layers above reuse those entries rather than producing new ones. Storage falls by roughly the reuse factor, and each layer still keeps its own query and its own local sliding-window state.

04 · The headline change

CED: an encoder half and a decoder half

Global KV is projected from the middle of the network, not computed at the top.

V4.1 splits the transformer into two zones. The bottom L/2 layers are the causal encoder and behave normally. For every layer above that boundary — the decoder — the key/value entries are not derived from that layer's own hidden state. They are projected directly from the encoder's final hidden state using a per-layer weight matrix.

Standard:   Cl = Hl · WlKV    (layer l builds its own)
CED:         Cl = HL/2 · WlKV    for all l > L/2   (the midpoint builds for everyone)

result 1

Half the prefill depth

The decoder's global KV can be produced without running the decoder's attention over the full sequence. Prefill complexity falls from O(N·L) to O(N·L/2) — effectively halving it.

result 2

Asymmetric activation

The model activates 8B parameters during prefill but 16B during decode. Read-heavy agent workloads — which resend long contexts constantly — pay the smaller number on the part that dominates their bill.

result 3

Local attention stays deep

CED only shares the global branch. Sliding-window attention is still computed per layer from each layer's own hidden state, preserving local computational depth — the part that carries fine-grained syntax.

The catch, stated plainly. Sharing global KV across layers means those layers no longer each have their own view of the sequence. CED compensates by keeping the per-layer local (SWA) path intact, and by giving the encoder half full computational depth. The published result is "comparable performance to the baseline" while roughly halving prefill — a trade, not a free lunch.

Why half is possible

Because the decoder's global KV is a projection of a hidden state that already exists, producing it costs one matrix multiply — not a full attention pass over the sequence. The expensive part of a layer is skipped, not the layer itself.

What still runs at full depth

Sliding-window attention, in every layer. It is local, so its cost does not grow with total context — but it does depend on each layer's own hidden state, which is why the decoder must still be evaluated to produce it. V4.1 handles that with bounded replay rather than by caching it.

06 · Cache compression

CSA2: three modes, one shared cache

Some layers compute the KV. Most layers borrow it. A few also borrow the selection.

Compressed Sparse Attention 2 stacks compression along three independent axes — the size of each entry, the number of entries along the sequence, and the number of layers holding their own copy. Each CSA2 layer is statically assigned one of three modes.

Full Mode

computes
reuses
cost

The decoupling is the trick. Sharing the cache and reusing the selection are separate decisions. That lets most layers skip the storage cost of KV and most layers skip the compute cost of indexing, while still allowing the selection to change as you go deeper — which a single global routing choice would not permit.

What compression along each axis looks like

sequence axis

Every m token positions are merged into one compressed entry, weighted by learned compression scores. Sequence length divides by m.

head axis

Multi-query attention shares one key/value across all query heads, so the cache scales with query heads only for the queries — not the KV.

layer axis

Layers reuse a preceding layer's KV and indexer keys. The number of distinct caches in the stack drops to roughly the number of Full-mode layers.

07 · Finding the needles

The indexer decides what a layer reads

Before sparse attention can be cheap, something has to pick the top-K entries — and that picker is itself O(n).

Sparse attention only reads a few compressed entries per query. A small lightning indexer scores every candidate and selects the top-K. But scoring every candidate is linear in context — at a million tokens, that scan becomes the new bottleneck.

V4.1's Hierarchical Sparse Indexer restricts the search domain for deeper layers using work the first layer already did, with no extra state.

The hierarchy

The numbers from the report

block selection
Each block takes the maximum index score of its positions; the highest-scoring blocks are kept.
example pool
2,048 blocks × 8 positions = 16,384 candidate positions.
final selection
Each reindexing layer picks its own top-512 from within that pool.
effect
For a fixed pool size, per-query indexer cost goes from linear in context length to constant for every layer after the first.

Honest scope. The first Full-mode layer still scans the entire causally visible range. Hierarchical indexing makes later evaluations constant-cost; it does not remove the initial full-range pass. And it is decoder-only, and introduced during post-training — the candidate restriction is applied identically in training and inference so the indexers are optimized under the domain they will actually see.

08 · Cache arithmetic

Where 890 bytes per token comes from

Three multiplicative reductions, applied on top of each other.

× layer reuse

Layers stop each keeping their own global KV and indexer keys. Only the Full-mode layers produce them.

× sequence compression

Every m positions collapse into one compressed entry, so there are fewer entries to store at all.

× FP4 precision

Each entry is stored at roughly four bits instead of eight, nearly halving bytes per entry.

Global KV per token — the published comparison

The report states V4.1-Flash's global KV cache (always resident in HBM) is 890 bytes per token, roughly ¼ of DeepSeek-V4-Flash at the same sequence length, and that its persistent footprint (SSD or host memory) falls to roughly ⅛. It also reports a ~437× reduction in per-token global KV relative to DeepSeek-V1.

Why this beats shrinking the model. Parameter count affects compute. Cache size affects whether you can serve the request at all, and how many concurrent requests fit on one GPU. At long context the cache, not the weights, is what runs out first — which is why V4.1 is larger than V4-Flash (552B backbone vs 284B) yet cheaper to run at length.

09 · Precision

Four bits, carefully placed

Quantize after RoPE, dequantize before attention, and keep the local cache at FP8.

The chosen format

format
MXFP4 — the OCP standard, chosen for hardware portability.
layout
E2M1 values with one E4M3 scale per 16 channels (NVFP4-style), minus the second-level global scale.
why no global scale
After RMSNorm the KV latent's norm is bounded near √512 ≈ 22.6, and observed maxima sit around 10 — far below the format's ~2688 range. Omitting the scale costs no measurable accuracy and simplifies the layout.
quantize after RoPE
Quantizing before RoPE helps only marginally and adds decode overhead, so the cache is quantized after rotation.
SWA cache stays FP8
The sliding-window cache is more sensitive to quantization and is kept at higher precision.

Why storage-only quantization works

The cache is dequantized before attention runs. That means the format never has to be supported by a matrix-multiply unit — it only has to survive a round trip through memory. This is what lets V4.1 use a more accurate four-bit layout than the hardware's native FP4 path would allow, and stay portable across accelerators.

Two separate wins

FP4 indexer Q/K (already present in V4) accelerates the index computation itself. FP4 main KV (new in V4.1) reduces storage, not math. Different mechanisms, different bottlenecks.

10 · Deployment

SWA Bounded Replay: replay a window, not a stack

Instead of persisting the local cache, recompute a little of it — and accept an approximation.

Sliding-window attention in every layer means the local cache depends on every layer's own hidden state. Reconstructing it exactly would require replaying L × nwin tokens — one window per layer. V4.1 instead replays only the most recent nwin tokens and truncates SWA to that segment.

EXACT RECONSTRUCTION
replay tokens = L × nwin
e.g. 60 × 4,096 = 245,760 tokens

Mathematically identical to a full forward pass, but the SWA cache must be persisted to SSD to avoid paying this cost — and SSD capacity and bandwidth become the binding constraint.

SWA BOUNDED REPLAY
replay tokens = nwin
e.g. 4,096 tokens

No SWA cache persisted at all. A query at position i attends to keys in [max(s, i−W+1), i] for replay start s. States are approximate, so results depend on where the cache hit landed.

The approximation is real and disclosed. The reconstructed state is not mathematically equivalent to a full pass, and by design the global KV computed for the uncached suffix depends on the cache-hit position. The report's claim is empirical: the impact on response quality is negligible. They also simulate the same replay during post-training so the model adapts to it — train-aware, not a post-hoc hack.

Two flavours

Encoder SWA Replay
Makes prefix caching depend only on global KV, so SWA KV can be removed from the persistent cache entirely.
Decoder SWA Replay
Bounds the decoder forward pass to nwin tokens, nearly halving total prefill computation.
11 · The residual stream

Widening the highway, then fusing it

From one residual lane to several, updated in a single kernel.

Recall from Part 1 that the residual stream is a single wide vector that every block adds into. DeepSeek V4 introduced hyper-connections (mHC): instead of one stream, keep n parallel streams and let learned mappings decide how they mix around each block. The constraint ("manifold- constrained") exists to keep signal propagation stable across depth.

STANDARD RESIDUAL
xl+1 = xl + Fl(xl)

One lane. Each block reads it, computes, and adds back. Simple, stable, and the only scaling axis it offers is width and depth.

VS
HYPER-CONNECTIONS
Xl+1 = BlXl + ClFl(AlXl)
(Al,Bl,Cl) = H(Xl)

Several lanes, with learned input, residual, and output mappings. The inner layer still sees a normal-width vector, so depth costs nothing extra — this is a complementary scaling axis.

V4.1's contribution: Single-Pass mHC. The original mHC needs four kernels to execute the update. V4.1's single-pass version plus its Mega-mHC deployment kernel halves activation memory traffic. Nothing about the math changed — this is a pure systems win, and it is a good example of how much of frontier inference cost lives in kernel fusion rather than architecture.

12 · Memory that isn't math

Engram: 196B parameters you don't multiply

Look up n-gram knowledge by hash instead of recalling it through a matrix multiply.

Storing facts in MLP weights is expensive: every retrieval costs a full-width matrix multiply at every layer. Engram is a conditional memory module that decouples memorization from computation — knowledge lives in hash-indexed embedding tables that are addressed, not computed over.

The configuration, as published

parameters
196B, split evenly across two modules
n-gram orders
{2, 3, 4} per module

embedding dim
2048 per order
table size
~16M entries per head, sizes chosen as distinct primes to reduce collisions
precision
FP8 for embedding tables and key/value projections
placement
Layers 1 and 14 (zero-indexed) — chosen to balance memory across pipeline stages

Why "conditional"

Context-aware gating decides how much the retrieved memory contributes at each position. It is not a static lookup bolted on — the module reads context to modulate its own output.

The serving trick

Because addressing is deterministic — same n-gram, same slot — the embeddings can be prefetched from host memory by background RDMA transfers. Prefetching for the first module overlaps with computation in the first transformer block, so the lookup is largely hidden behind work that was happening anyway.

That is a genuinely different lever: 196B parameters that cost bandwidth but almost no FLOPs.

Two changes from the original Engram

The short causal convolution was dropped (gains did not justify inference-stack complexity), and embedding updates use momentum followed by Sinkhorn balancing instead of Adam — which avoids a large optimizer-state footprint.

13 · Decode latency

DSpark: guess five tokens, verify cheaply

Speculative decoding, rebuilt with a confidence model and a load-aware scheduler.

Decode is sequential: one forward pass per token. Speculative decoding breaks that by having a small draft model propose several tokens, then checking them against the real model in one pass. Every accepted token is a forward pass you did not have to run.

semi-autoregressive

Three transformer blocks with a 128-token sliding window produce base logits for five draft positions in a single forward pass. A lightweight Markov head then models the dependencies between those draft tokens.

confidence head

Predicts per-position conditional acceptance probabilities, which are combined into prefix survival probabilities — "how far into this draft will we actually get?"

the scheduler

Combines those estimates with profiled engine throughput curves to pick the verification length per request, maximizing expected system-wide token throughput under current load. Verification depth becomes an economic decision.

How it differs from V3's MTP. V3's multi-token-prediction module trained jointly with the backbone throughout pretraining. DSpark is introduced in a dedicated stage after pretraining with the backbone frozen, then continues training alongside it during post-training without gradients flowing back into the backbone. That keeps the drafter aligned with a policy that keeps changing — so it accelerates both live serving and the rollout generation used for RL.

Resolution handling

Absolute positional embeddings are replaced with 2D-RoPE so the encoder handles varying resolutions natively. After the 3×3 unshuffle the model supports inputs up to roughly 1344 × 1344 pixels without the token count exploding.

Modality-aware load balancing

Image and text tokens have different representation distributions and therefore different expert-routing preferences. Balancing their aggregate load would hide modality-specific imbalance — so V4.1 keeps separate expert-wise correction biases for text and image tokens, updated independently, while retaining the original routing scores for weighting expert outputs.

15 · The payoff

Decode cost stops growing with context

Extend the context 256× and decode FLOPs rise by about a quarter.

This is the single most striking claim in the V4.1 report. Across a 256-fold increase in context — from 4K to 1M tokens — its single-token decode FLOPs increase by only about ¼. Earlier generations grow far faster. The chart below is drawn from the report's stated comparison.

Schematic of the report's stated trend: V4-Flash's decode FLOPs grow with context; V4.1-Flash's stay nearly constant. FLOP accounting weights BF16, FP8, and FP4 operations at 1, 0.5, and 0.25 respectively.

Why "nearly constant" is the important phrase. If per-token decode cost is flat in context length, then serving a 1M-token agent session costs almost the same per generated token as serving a 4K chat. That changes which products are economically viable — long-horizon agents, whole-repository code work, cross-document analysis — rather than merely making existing ones cheaper.

17 · Interpretation

What this actually buys — and for whom

The architecture is shaped by one workload: long-horizon agents.

V4.1's design only makes sense against a specific traffic pattern, and the report says so explicitly: agentic workflows generate extensive prefill requests, and KV cache misses impose severe computational overhead. Read-heavy, tool-calling, prefix-shared, very long contexts. Every one of the eight changes serves that shape.

For the operator

  • Cache-hit charges dominate agent cost — compressing the cache cuts them directly.
  • Off-peak rates are half of peak, so flexible workloads should be scheduled off-peak.
  • Fewer bytes per session means more concurrent sessions per GPU.

For the user

  • Longer contexts become routine rather than a special mode.
  • Per-token cost stops scaling with how much history you carry.
  • Native vision means screenshots and documents go in directly.

The strategic read. V4.1-Flash has more backbone parameters than V4-Flash (552B vs 284B) and outperforms V4-Pro on performance, cost, speed, and total runtime. That combination — bigger model, cheaper to run — is only possible because the bottleneck moved. When storage and bandwidth bind, reducing bytes beats reducing weights.

18 · Caveats

What to be careful about

Approximations are real

SWA Bounded Replay produces states that are not mathematically equivalent to a full forward pass, and results depend on the cache-hit position. The claim is empirical negligible degradation, not exactness.

The first indexer still scans everything

Hierarchical indexing makes later indexers constant-cost. The first Full-mode layer still does a full-range pass, and hierarchical indexing is decoder-only.

CED trades depth for prefill

Layers above the boundary no longer each hold their own global view. The design compensates with per-layer local attention and full encoder depth, and reports comparable performance — but it is a trade.

Engram costs bandwidth

196B parameters of memory that is prefetched rather than multiplied still have to move. The design hides it behind compute, but it is not free.

Model lineup is moving

DeepSeek has stated V4-Pro requests are being routed to V4.1-Flash at V4.1-Flash rates until V4.1-Pro launches, and that it is phasing out V4-Pro. Check current documentation before pinning a model ID.
